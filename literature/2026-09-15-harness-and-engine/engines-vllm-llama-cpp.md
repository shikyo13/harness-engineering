# Engine techniques: vLLM and llama.cpp vs mlx-serve

Shallow clones (`--depth 1`) pulled 2026-09-15: `vllm-project/vllm`, `ggml-org/llama.cpp`. mlx-serve version checked via `mlx-serve serve --help`: v26.9.2.

## Technique comparison

| Technique | Source (file:line) | What it buys | mlx-serve equivalent |
|---|---|---|---|
| llama.cpp cache-reuse (KV shift) | `common/arg.cpp:3569` (flag); `tools/server/server-context.cpp:3227-3237` (impl) | Reuses KV for a prefix that changed mid-prompt: matching chunks get shifted to their new position instead of recomputed. Needs `--cache-prompt`. | No. Closest is the hot prefix cache (`--prefix-cache-entries`/`--prefix-cache-mem`, exact-prefix match only) and `--ssm-checkpoint-stride`. Neither handles a chunk that moved; both need the prefix itself untouched. This is the gap that maps directly onto the tool-list pain point. |
| llama.cpp prompt cache + slot save/restore | `common/arg.cpp:3556` (`--cache-prompt`); `tools/server/server.cpp:285-286` (`/slots` routes); `server-context.cpp:5298,5334` (save/load), gated on `--slot-save-path` | Explicit per-session KV snapshot to disk, restored by slot id. | Yes, more automatic: `--prefix-cache-disk` persists every seen prefix by hash under `~/.mlx-serve/kv-cache`, no explicit slot-id API needed. |
| llama.cpp speculative decoding (draft model, lookup/ngram) | `common/arg.cpp:4228` (`--spec-draft-model`/`-md`); `4246-4402` (`--spec-ngram-mod-n-*`, `-simple-*`, `-map-k-*`) | A draft model or n-gram table proposes several tokens; target model verifies in one pass. | Yes, both: `--drafter <dir>` (Gemma cross-attention or DFlash draft model) and `--pld` (n-gram prompt lookup, on by default; `--pld-draft-len 5`, `--pld-key-len 3`). |
| llama.cpp KV cache quant types | `common/arg.cpp:2434` (`-ctk`), `2447` (`-ctv`) | Shrinks KV memory with per-tensor types (q8_0, q4_0, f16). | Yes, and further: `--kv-quant {off,4,8,turbo2,turbo4}`. turbo2/turbo4 are Hadamard-rotated, lower distortion than plain affine quant at the same width. Currently `off` in serve.sh. |
| llama.cpp MoE expert CPU offload | `common/arg.cpp:2750` (`-ot`/`--override-tensor`), `2755` (`-cmoe`), `2763` (`-ncmoe`/`--n-cpu-moe`) | Keeps MoE expert weights in system RAM; only active layers cross to VRAM, so a MoE model fits in less VRAM. | Not applicable as-is: unified memory has no separate VRAM to spill from. Closest lever is `--ane-prefill` (Neural Engine offload, qwen3_5 family only; this checkpoint is qwen4_exp) and the wired-memory budget in serve.sh itself. |
| llama.cpp Metal flash attention | `common/arg.cpp:1751` (`-fa`/`--flash-attn on\|off\|auto`); kernel at `ggml/src/ggml-metal/kernels/fa.metal` | Fused attention kernel: less memory traffic, smaller activation footprint. | No flag exposed. MLX's own fused attention is presumably always on, not a separate user knob. |
| vLLM V1 prefix caching (block hash, eviction) | `vllm/v1/core/kv_cache_manager.py:265` (`get_computed_blocks`); `kv_cache_coordinator.py:461` (`find_longest_cache_hit`); `block_pool.py:802` (`evict_blocks`), `:184` (LRU `free_block_queue`) | Exact-prefix block match across requests, hash-keyed, LRU eviction under a block budget. | Yes: `--prefix-cache-entries 128`/`--prefix-cache-mem 6GB`, an LRU with a byte budget, plus an SSD tier (`--prefix-cache-disk`) vLLM lacks natively. |
| vLLM V1 chunked prefill budget | `vllm/config/scheduler.py:49` (`max_num_batched_tokens` default); `v1/core/sched/scheduler.py:584` (`input_budget`), `:661-662` (`long_prefill_token_threshold` caps one request's chunk) | Caps tokens per scheduler step so a long prefill interleaves with other requests' decode instead of blocking the batch. | Partial: `--prefill-chunk 4096` caps a chunk's own size (also the SSM checkpoint stride on MoE targets). Single-tenant harness, so the multi-request interleaving half of vLLM's design does not apply here. |
| vLLM V1 speculative decoding (ngram, EAGLE, MTP) | `vllm/config/speculative.py:73` (`"ngram"`, `prompt_lookup_min/max` default 5 near `1176`); `:70` (eagle family); `:56,1121-1125` (`"mtp"`, older aliases fold into it) | Same three families as llama.cpp and mlx-serve. | Yes for ngram (`--pld`) and MTP (`--mtp`, forced on for this MoE target, naming matches vLLM directly). No EAGLE-style hidden-state drafter; `--drafter`'s Gemma/DFlash path is architecturally closer to a plain draft model. |
| vLLM V1 fp8 (and lower) KV cache | `vllm/config/cache.py:38-55` (`CacheDType`: `fp8`, `fp8_e4m3`, `fp8_e5m2`, `nvfp4`, `turboquant_k8v4`, `turboquant_4bit_nc`, `int4_per_token_head`, ...) | Shrinks KV memory, several numeric formats depending on GPU support. | Yes in spirit, not fp8 literally: `--kv-quant turbo2`/`turbo4` is the same Hadamard-rotation idea as vLLM's own `turboquant_*` types. Apple GPUs have no native fp8 path. |
| vLLM Metal or MLX backend | `vllm/platforms/` (`cpu.py`, `cuda.py`, `rocm.py`, `tpu.py`, `xpu.py`, `zen_cpu.py`, `interface.py`) | N/A | No. No `metal.py` or `mlx.py` in the platform list; confirmed absent in this clone. |

## Ranked experiments for this machine

1. **Baseline the tool-list re-prefill cost first.** Before touching flags, run two `probe.sh`-style calls through the same warm session, the second with one extra entry in the `tools` array. Compare TTFT and watch the server log for a full re-prefill vs. a partial hit. Every experiment below should be judged against this number, since it is the stated top pain point and no flag here fixes it directly.
2. **Try `--prefill-chunk 8192`** (up from 4096). serve.sh already flags this as the next thing to try "with a cold-prefill measurement in hand." Change the flag, run a cold 60k+ token request through `probe.sh` timing `chat/completions`, and watch wired memory against the 102 GB peak noted at 4096. Revert if it nears the 110100 MB Metal ceiling.
3. **Try `--kv-quant turbo4`.** Frees KV RAM that currently competes with the 30 GB n-gram table for page-cache residency (only 11 GB resident today). Costs one cold prefill since the cache namespace resets. Run `probe.sh` right after the switch and again warm, comparing `tokens_per_second` and TTFT to the `off` baseline.
4. **Lower `--prefix-cache-mem` (try 3GB) and lean on the disk tier.** Wired memory is already full; this is a direct lever on it, and SSD restore costs seconds against minutes for re-prefill. Measure warm-turn TTFT with `probe.sh` on a session just evicted to disk, and check whether n-gram table resident bytes rise in the log.
5. **Confirm the effective `--ssm-checkpoint-stride`.** serve.sh notes MoE targets already raise the effective stride to the prefill-chunk size; verify this in the startup log, and if experiment 2 changes chunk size, recheck restore granularity on a project-switch prompt. Measure with `probe.sh` on a resumed session, expecting partial restore rather than a cold prefill.
6. **Harness-side: stabilize the tool list instead of relying on the engine.** mlx-serve has no `--cache-reuse` equivalent, so the only fix is to stop the prefix from changing: render a stable superset tool block, or append new tools after a fixed anchor. Validate with experiment 1's same diff, repeated after the harness change.
