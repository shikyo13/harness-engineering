# 02 — Competitor audit: Crush (Charm)

Audited 2026-10-13. Repo `Datasets/harness-research/repos/crush`, head `d6edc3222231a0177b88d073733413578c9a1e01` (2026-10-13, merge of PR #3924 "server: scope permission/question prompts to the current session"). Shallow snapshot (1 commit), so all claims are from reading the head tree; **[source-verified]** unless tagged **[doc]**. The tool-loop engine is the external module `charm.land/fantasy` v0.45.1 (go.mod:10); its pinned copy in this machine's Go module cache was read directly and is cited as `fantasy:<file>:<line>`.

Comparison frame from `01-ZERO_CODE_BASELINE.md`: Zero Code ships a ~1,900-line `while(true)` V1 loop, a 9-stage edit matcher cascade, tree-sitter bash permissions, shadow-git checkpoints, and an experimental-off LSP tool. Crush is the most direct structural peer: Go, TUI-first, SQLite sessions, and *LSP tools on by default*.

## 1. Architecture

- Client/server split inside one binary. TUI (`internal/ui`) talks to an in-process `Backend` (`internal/backend/backend.go`, 1,188 lines) through an SSE + REST/proto server (`internal/server/`); a workspace is per-working-dir and supports multiple attached clients (`internal/workspace/client_workspace.go`, `multiclient_integration_test.go`). The same backend serves a headless mode (`crush run`) and channels (chat integrations; `internal/agent/channel.go`, `channelreply.go`).
- Session agent (`internal/agent/agent.go`, 2,428 lines) is per-session and serializes runs: a per-session mutex makes the dispatch decision (cancel-on-entry / queue / active) atomic against `Cancel` (`agent.go:623-693`); queued prompts are drained and *folded into the current step* at each `PrepareStep` (`agent.go:881-889`), while prompts carrying their own RunID run as separate recursive turns (`agent.go:766-771`). This is Zero Code's steer/queue vocabulary, implemented for V1.
- The loop itself is `fantasy.NewAgent(...).Stream(...)` (`agent.go:728-733, 844`) — an external, ai-sdk-flavored step engine with callbacks (`PrepareStep`, `OnTextDelta`, `OnToolCall`, `OnToolResult`, `OnStepFinish`, `StopWhen`). Crush supplies durability, permissions, LSP, storage; fantasy supplies the loop.
- Storage: SQLite via goose migrations (`internal/db/migrations/`, 12 files, initial 2025-04) + sqlc-generated queries (`internal/db/sql/*.sql`); two pure-Go driver build tags, modernc (`connect_modernc.go:20`) and ncruces (`connect_ncruces.go:28`). Tables: sessions (with `Todos`, `SummaryMessageID` — `internal/session/session.go:59-61`), messages (parts as JSON), `files` (versioned file snapshots, `internal/history/file.go:65`), `read_files` (persistent read tracker), `mcp_enabled/disabled` (per-repo MCP allowlists).

## 2. Key techniques (source-verified)

**Loop mechanics / streaming tool calls.**
- Per-step tool dispatch is deferred until the provider stream ends: raw tool calls are buffered, and on abnormal finishes (length/content-filter/error) they are recorded but *never repaired or dispatched* — truncated arguments never execute (`fantasy:agent.go:1612-1723`, "CHARM-2020" comments). Zero Code has output-truncation handling but executes parsed calls more eagerly.
- Each validated call goes through `validateAndRepairToolCall`, which may make an extra model call to fix malformed arguments (`fantasy:agent.go:1741`); crush additionally pre-sanitizes non-JSON tool input and turns it into an instructive error result (`agent.go:1004-1006, 1023-1025, 2417`).
- Parallelism is per-tool opt-in (`Info().Parallel`): parallel calls run under a 5-slot semaphore, non-parallel calls hold a global mutex — so crush's local tools are effectively serial (`fantasy:agent.go:1662-1706`). Only network-ish tools declare parallel: fetch/web_fetch/web_search/download/sourcegraph/MCP-resource reads and the subagent tool (`tools/fetch.go:58`, `tools/web_search.go:36`, `agent_tool.go:40`). Tool ordering is preserved by splicing results into emission positions (`fantasy:agent.go:1725-1740`).
- Panic containment: every tool runs through `runToolSafely`, converting panics into error results (`fantasy:agent.go:882-898`).
- Stop conditions (`agent.go:1095-1120`): (a) auto-summarize when `remaining ≤ threshold`, threshold = 20k tokens for windows >200k else 20% of window (`agent.go:56-58, 1096-1116`); (b) doom-stop on repeated tool interactions: SHA-256 of (tool name+input+result) per step, >5 identical signatures in a 10-step window halts (`loop_detection.go:12-64`). Stronger than Zero Code's doom-loop in one way: the signature includes the *result*, so only truly non-progressing repeats count.
- Streaming durability: assistant message is created per step in `PrepareStep` and updated on every delta; tool results are separate durable `message.Tool` rows created at result time (`agent.go:917-933, 1021-1039`); on cancel/error, persistence uses `context.WithoutCancel` + 5 s flush so final state lands even during shutdown (`agent.go:792-824, 1148-1156`). A `RunComplete` terminal event (with text reconciliation) is must-deliver per run (`agent.go:805-823`). Still: run state is in-memory (`activeRequests` map); a process crash leaves no durable "run interrupted" record — same gap as Zero Code finding #3.
- Anthropic prompt-cache placement: cache-control on the last system message boundary and the last two messages, plus the final tool (`agent.go:723-726, 893-907`). Cruder than Zero Code's frozen-prefix scheme but same goal.
- Provider retries with backoff log + `OnRetry` resets partially streamed content so a retried response doesn't concatenate onto the failed attempt (`agent.go:985-995`); auth-refresh callback hook for OAuth/SSO mid-turn (`agent.go:996`, `aws_sso_refresh.go`).

**Tools and edit approach.**
- `edit` is exact-match with one fallback tier: whole-line whitespace-normalized matching only (`edit_whitespace.go:26-66`) — far simpler than Zero Code's 9-stage cascade, and honest about it (fail fast rather than 65%-similarity region replacement).
- Read-before-edit is *enforced in code*: `filetracker.LastReadTime` must be non-zero and newer than the file's mtime or the edit is rejected with "use the View tool first" (`edit.go:288-302`); the tracker persists in the `read_files` SQLite table across restarts. This directly fixes Zero Code baseline finding #4 (unenforced read-before-edit).
- After every write the tool notifies LSPs and appends fresh diagnostics to the tool response (`edit.go:97-100`); CRLF normalized to LF for matching, restored on write (`edit.go:307-311`).
- Undo: every edit creates a versioned snapshot row in `files` (`history/file.go:58-84`), the SQLite equivalent of Zero Code's shadow-git.
- `bash`: hard ban-list steering the model to tools instead (curl/wget/ssh/sudo/package managers rejected; `bash.go:75-130`); description param required; auto-backgrounds after 60 s default with `job_output`/`job_kill` follow-up tools (`bash.go:54, 319-321`); 30k output cap (`bash.go:53`). Execution goes through an embedded POSIX interpreter `mvdan.cc/sh/v3` with an in-process `jq` builtin — same shell semantics on Windows (`shell/shell.go:6, 21-23`, `builtins_registry.go:19`). Not a persistent interactive shell; each execution is independent (`shell.go:4`).
- Web: `search` is DuckDuckGo HTML (`search.go:18`), `sourcegraph` for public-code search, `fetch`/`agentic_fetch` (sub-model summarization).

**LSP integration — the headline differentiator (all on by default).**
- Eight agent tools: `lsp_symbols` (document outline), `lsp_definition`, `lsp_references` ("more accurate than grep for code symbols", `references.md`), `lsp_rename`, `lsp_call_hierarchy`, `lsp_diagnostics`, `lsp_replace_symbol`, `lsp_restart`. `lsp_replace_symbol` resolves symbol ranges via documentSymbol and edits by range — "eliminates whitespace-matching failures" for whole-symbol changes and returns diagnostics afterwards (`lsp_replace_symbol.md`). This is a *replacement* of grep+text-edit for structural changes, not an annotation of them.
- Lazy lifecycle: any LSP tool call triggers `Manager.Start(ctx, path)` for that file (`lsp_symbols.go:31`), starting only servers that pass all three gates: file type matches, project root markers present (`handlesFiletype`/`hasRootMarkers`, `manager.go:334-371`), and the server binary is on PATH.
- Auto-start safety valves: a 26-entry skip-list refuses too-generic launcher commands (`python`, `node`, `deno`, `dotnet`, `ruff`…) because resolving them would start the wrong thing (`manager.go:124-152`); `recentlyUnavailable` caches PATH-miss failures with a retry delay so cold tool calls don't rescan PATH per server (`manager.go:286-303`); a user's explicit config bypasses the `AutoLSP=false` kill-switch (`manager.go:153-160`).
- The catalog is Charm's `github.com/charmbracelet/x/powernap` v0.1.6 default server set (cached at `config/load.go:668-687`), user-overridable per-server in `crush.json` (`config/config.go:527, 848`, `AutoLSP` default true at `:477`); editor-grade doc sync: `OpenFile`/`NotifyChange`/`RefreshOpenFiles`/`WaitForDiagnostics` (`lsp/client.go:402-624`), signature preservation for reasoning (below).
- Defaults: LSP tools are in the default tool set and the read-only/plan-mode subset (`config.go:1036-1043, 1068, 1081-1083`).

**Sessions, compaction, MCP, rules.**
- Auto-compaction is stop-the-world: `Summarize` runs one big-model call over the whole tail with a structured handoff prompt (`templates/summary.md`: current state / files & changes / technical context), stores an `IsSummaryMessage` row, and subsequent loads read only from the summary marker (`agent.go:1411-1470`, `getSessionMessages` `agent.go:1792-1815` — summary message is re-injected with role flipped to user). Summary prompt includes outstanding todos (`buildSummaryPrompt`, `agent.go:2382`).
- MCP: per-repo enable/disable persisted in DB and filtered per turn (`agent.go:1717-1743`); connected servers' initialize instructions are appended to the system prompt in an `<mcp-instructions>` block (`agent.go:709-721`); resource tools `list_mcp_resources`/`read_mcp_resource`; coordinator gates first runs on MCP readiness (`coordinator_readiness_test.go`, `coordinator_mcp_gate_test.go` [doc: tests show intent, gate verified indirectly]).
- Rules: default global context paths are `~/.config/crush/CRUSH.md` and sibling `AGENTS.md` (`config/load.go:577-586`), plus project `ContextPaths` and skills dirs (`load.go:627-640`); Claude-compatible hooks (`EventPreToolUse`, `internal/hooks/hooks.go:15`; extensive hooks docs [doc]).
- **Accepted-run protocol** (durability at the admission boundary): callers can `BeginAccepted(sessionID)` to reserve a run before dispatch (`agent.go:344-366`); every accept gets a monotonic `seq`, cancel marks sessions with a `canceledBySeq` watermark, and an accepted run that discovers it was canceled *before* streaming persists a synthetic canceled turn and still publishes its terminal `RunComplete` so external waiters never hang (`agent.go:634-661, 532-576`). Queued prompts that arrive after the watermark survive (`agent.go:870-880`). This is the closest external analogue of Zero Code's durable `session_input` admission, though the reservation is in-memory, not a DB row.
- Model plumbing: catalog + provider metadata come from `charm.land/catwalk` (auto-updated provider/model registry, like an LLM-index); per-step OpenRouter cost passthrough (`agent.go:1978`) and Hyper-routed model/credit attribution extracted from provider metadata (`extractPrismModel`, `agent.go:1994-2021`); per-model context window drives summarize threshold (§2 Stop conditions).
- Plan mode is a tool-subset, not a separate loop: `resolvePlanTools` whitelists agent/glob/grep/ls/question/sourcegraph/view + the three read-only LSP lookups for the plan agent; a separate `resolveReadOnlyTools` set gates read-only sessions (`config/config.go:1064-1089`), with `plan.md.tpl`/`task.md.tpl` prompts per agent type (`agent/templates/`).
- Head commit (the "workspace prompts" PR): SSE fan-out is now session-scoped for interactive prompts. `sessionScopedEventID` marks permission/question request+notification events; `deliverToClient` delivers them only to clients whose reported current session matches, resolving subagent sessions to the root session, dropping them for clients on the landing screen, and failing *open* for API clients that never report a session (`server/events.go:176-241`; client session reporting endpoint `server/endpoints.go:77`). Fixes the multi-client "session steals another's permission dialog" bug class in a 30-line filter — worth stealing wholesale.
- Subagents: `agent` tool runs a configured task-agent as a child session, parallel-flagged, with cost rolled up to the parent (`agent_tool.go:26-60`, `coordinator.go:1655-1658`); parent resolution reused by the prompt router above.

**Self-observability and honest accounting.**
- Two introspection tools: `crush_info` (live runtime state — active model/provider, LSP+MCP server health, skills, hooks, permission mode, disabled tools; `tools/crush_info.md`) and `crush_logs` (recent log tail, `tools/crush_logs.go`). The agent can diagnose its own substrate mid-session — Zero Code has the telemetry ledger but nothing in the loop can query it (baseline finding #7).
- Usage fallback: when a provider returns zero usage, step usage is *estimated* from the prepared messages and the estimate is flagged (`fallbackStepUsage`, `agent.go:1086`, `usage_fallback.go:18`; `updateSessionUsage(..., estimated)` carries the flag into the session counters, `agent.go:2036`).
- Encrypted/signed reasoning round-tripping is preserved across turns: Anthropic reasoning signatures, Google `thought` signatures (with owning tool ID), and OpenAI Responses reasoning items are captured at `OnReasoningEnd` and persisted on the message (`agent.go:942-961`), enabling stateless replay of thinking blocks.
- Provider media-limitation workaround: on non-Anthropic/Bedrock providers, images carried inside *tool results* are extracted out of the tool message and re-attached as user-file parts so strict providers don't reject history (`workaroundProviderMediaLimitations`, `agent.go:2295-2380`).
- Session title generation runs on a detached context in a goroutine from the first real user prompt, so it can't delay or be killed with the run (`agent.go:746-753`, `GenerateTitle` `:1833`).
- Channel replies: completed-tool-call bookkeeping per turn decides whether the model already answered on the originating chat channel, avoiding double replies in channel mode (`agent.go:834-838, 1027-1029`; `channelreply.go`).

## 3. Strengths

1. Only audited competitor (besides Zero Code's off-by-default tool) with a *first-class LSP surface*, and the only one with symbol-range editing that removes text-matching from whole-symbol changes entirely.
2. Auto-summarize threshold, doom-loop signature over call+result, non-dispatch on abnormal finish, retry stream reset — small, high-leverage loop invariants, all unit-tested.
3. Enforced read-before-edit with a persistent read tracker and mtime staleness; versioned snapshots in the same SQLite DB as sessions (one durability substrate).
4. Battle-tested cancellation semantics: run-ID accept protocol, per-seq cancel marks, queue drain with cancel coverage, `WithoutCancel` persistence flushes — ~15 race tests (`dispatch_race_test.go`, `cancel*`).
5. Headless-ready: every capability is reachable over SSE/REST with per-run terminal events, which is what makes multi-client and channel features possible at all.

## 4. Weaknesses

1. Loop engine correctness lives in an external module (`charm.land/fantasy`); the harness repo can't express session-aware scheduling (e.g. two edits to the same file serialize only because both are non-parallel — everything is non-parallel; independent `view`/`grep` pairs also serialize).
2. Effective tool parallelism ≈ none for local work: the parallel allow-list is network-only (`grep Parallel` above); a batch of reads pays serial latency.
3. Compaction is lossy and stop-the-world: whole-tail summary, fixed prompt sections, no verbatim tail selection or cache-continuation accounting; auto-summarize triggers purely on token arithmetic of the *previous* step's usage (`agent.go:1103`), so a huge single tool result can overshoot first.
4. Edit matcher has only two tiers (exact, whitespace-normalized whole-line); no fuzzy tier, no near-miss guidance — misses edits Zero Code's cascade would land, but also avoids Zero Code's 65%-similarity corruption risk. Trade-off is honest; neither is optimal.
5. No durable run status; crash mid-run is repaired only by message forensics. Loop detection only *stops* the turn (error), it doesn't redirect like Zero Code's doom-loop redirection.
6. LSP auto-start depends on user-installed servers and a static skip-list; no install flow in-agent (TUI offers it [doc: README]).
7. `search` (DuckDuckGo HTML scraping) is fragile by design; web research relies on optional Sourcegraph/API keys.
8. Three overlapping surfaces (TUI, SSE/proto server, chat channels) all consume the same permission/question stream; the head commit exists precisely because that fan-out had undefined semantics — evidence the multi-surface story is still stabilizing.
9. Loop-detection and summarize stop conditions are tuned constants with no per-model or per-session adaptation, and neither feeds a quality metric back (no equivalent of kimi's per-step decode ledger).

## 5. Works vs unproven

- **Source-verified working**: session-serialized runs with steer-fold; per-step durable streaming; loop detection; auto-summarize + summary-tail reload; read-before-edit enforcement; LSP lazy start + diagnostics-on-edit; SQLite store with migrations; session-scoped prompt routing (head commit, with e2e tests `internal/server/e2e_test.go`).
- **Test depth (source-verified)**: loop semantics carry dense unit/e2e coverage — dispatch-race, cancel, queued-run-ID, MCP-gate and coordinator tests in `internal/agent/*_test.go`; server e2e asserts attached-client accounting and per-session cancel isolation (`internal/server/e2e_test.go`, `e2e_agent_test.go`).
- **Source-verified (bash lifecycle)**: foreground command auto-converts to a background job after `auto_background_after` (default 60 s) with `job_output`/`job_kill` follow-ups and a `BackgroundShellManager` registry (`bash.go:29-31, 319-321`; `shell/background.go:74-238`); tests in `bash_test.go`, `job_test.go`.
- **Documented-only / not verified here**: multi-client + herdr terminal-multiplexer status integration beyond tests (`herdr/client.go` doc header); hooks runtime breadth (docs/hooks 759-line README [doc]); Hyper/Prism credit metering (present in code, provider-specific); MCP readiness gate exact mechanics (test names, not gate body).
- **Unproven**: compaction quality (no cache-hit accounting comparable to Zero Code's 98%/0% measurement); behavior with local 4-bit models (auto-summarize is skipped when context window unknown — `agent.go:1098-1101` — a deliberate local-model guard Zero Code should copy).

## 6. What Zero Code should learn

1. **Adopt symbol-range editing.** Ship `lsp_replace_symbol`-style range edits (documentSymbol boundaries → region replace + diagnostics append) as the primary structural-edit path when the LSP tool is on. It sidesteps the whole matcher-cascade corruption risk (baseline finding #4) for the exact case where fuzzy tiers fail worst.
2. **Gate LSP auto-start like the manager does**: file-type ∧ root-marker ∧ PATH-present, with a generic-command skip-list and unavailable-backoff — the missing operational piece in Zero Code's off-by-default LSP tool's on story.
3. **Include tool results in the doom-loop signature.** Crush's hash of (name, input, result) per step is strictly better than input-only repetition detection: retry-with-same-input-but-new-result isn't a loop.
4. **Never dispatch tool calls parsed from an abnormally-finished stream.** Truncation-time "arguments were cut mid-JSON" edits are a real corruption vector for Zero Code's eager settlement.
5. **Persistent read tracker + mtime check as an edit precondition** is cheap (one table, one stat) and closes the read-before-edit enforcement gap without touching the matcher cascade.
6. **Session-scoped interactive-prompt routing** (head commit) is a ~30-line pattern for Zero Code's server: tag permission/question events with session ID, deliver to viewers of that session (subagent→root), fail open for session-less API clients.
7. **Stop-the-world summarize threshold tuning by window size** (fixed 20k buffer above 200k windows, else 20%) and *skipping* auto-summarize for unknown context windows are directly reusable constants for local models.
8. **Give the agent a `crush_info`-equivalent** (one no-arg tool exposing engine/model/LSP/MCP/permission/disabled-tool state, plus a log-tail tool). It's the cheapest possible mitigation of baseline finding #7: the loop can consume its own observability, and mid-session "why is diagnostics empty" questions stop being user questions.
9. **Default long commands to background.** A per-call `auto_background_after` (60 s default) with `job_output`/`job_kill` means a blocking `npm install` never burns a whole turn's wall-clock budget; Zero Code has background jobs but nothing *moves* a foreground command into one automatically.
10. **Mark estimates as estimates.** Zero Code's cost/token accounting for local models should carry crush's `estimated` flag end-to-end rather than fabricating exact-looking numbers.
11. **Versioned file snapshots inside the session DB** (one `files` table, one substrate for history+undo+read-tracking) is worth mirroring in Zero Code's V2 store: shadow-git stays, but *undo-by-DB-row* gives per-step file diffs without git plumbing.
12. **Do not outsource the loop blindly.** Crush's biggest structural gift and biggest liability is the same thing — outsourcing the step engine to `fantasy` got them a well-tested provider/stream/tool-repair core, at the price of session-aware scheduling. Zero Code's V2 `SessionRunner` should keep the loop local so the kimi scheduler (lesson on accesses) and crush's result-aware doom-loop can coexist inside it.
