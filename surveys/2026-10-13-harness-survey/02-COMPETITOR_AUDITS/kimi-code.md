# 02 — Competitor audit: Kimi Code CLI (Moonshot)

Audited 2026-10-13. Repo `Datasets/harness-research/repos/kimi-code`, head `b510fa9aec85f02849f64121550be2c3fbd4294d` (2026-10-13, "feat(kap-server): add remote control device deletion" #4192). Shallow snapshot (1 commit); claims are **[source-verified]** from head-tree reads unless tagged **[doc]**. TypeScript pnpm monorepo; the real engine is `packages/agent-core-v2`, which vendors its own core library under `src/human/` (import alias `#human/*`, package.json:31). `packages/kosong` is a separate published LLM-adapter package with its own providers; both adapter stacks coexist.

Comparison frame from `01-ZERO_CODE_BASELINE.md`: this is the strongest "harness tuned to its own model" peer next to qwen-code, and the only audited one with a state-motor agent loop plus a first-class remote-control/multi-device story.

## 1. Architecture

- **The loop is literally an XState state machine.** `#human/agent/machine.ts` (949 lines) defines the agent machine — states `linking → restoring → idle → running → closing → disposed` (machine.ts:564-944), driving event-sourced history via an event store with a durable journal (engine.ts:10-12 imports `createEventStoreSync`, `memoryJournal`; `loop/machine/storeJournal.ts`). Each turn spawns a child **turn machine** (`#human/agent/turn.ts`, 886 lines) as an actor (machine.ts:741-752); each tool call in the turn is itself a spawned actor (`turn.spawn_tools → spawnTurnTools`, machine.ts:886-890). The typed durable event vocabulary is `MachineEngineEvent` (~25 event types: stepStarted, retrying, recovering, tool.detached, promptSteered, …) (`loop/machine/engine.ts:54-118`).
- **Turn machine = the provider-turn loop**: `gating` (before-step hook, e.g. compaction check) → `thinking` (invoke llm actor; accumulator folds streamed parts, supports `rollback()` for retries) → `acting` (collect per-tool outcomes; guarded transition to `draining` when every pending call settled) → `draining` (inject steered/reminder messages, then re-enter `gating`; `steps` counter **resets to 1 when new user messages arrive**, enforcing `maxSteps` only on tool-only continuation) → `done/failed/aborted` (turn.ts:429-886). Max-steps failure is `MaxStepsExceededError` (turn.ts:289-291, 844-848).
- `loopService.ts` (2,294 lines) wraps the machine with product behavior: prompt queue/channel (`promptChannel.ts`), `steer(promptIds)` (loopService.ts:364), prompt gating (runPromptGate :572), tool-result delivery into history (deliverToolResult :641), unknown-tool-call recovery (executeUnknownToolCall :1651), and an "engine refold" on session restore that rebuilds machine state from the journal (`onDidRestore` hook, loopService.ts:240; `agent/replayBuilder`).
- **Process topology**: TUI (`pi-tui`, differential rendering + CSI-2026 synchronized output, pi-tui/README [doc, code present]) → `klient` client SDK over in-memory or IPC transports (klient/package.json description) → core. `kap-server` exposes the same core over a full REST/WS API (~39 route modules: sessions, messages, approvals, terminals, tasks, workspaces, transcript, remoteControl…) for web/vscode/mobile. `acp-server` speaks the Agent Client Protocol (Zed). `apps/vis` is a session visualizer.
- **Plugins**: a plugin service inside the core (`agent/plugin/agentPluginService.ts`) plus a hosted marketplace (`plugins/marketplace.json`, official plugins `kimi-datasource` and `kimi-webbridge`; dev builds point at `code.kimi.com/kimi-code/plugins/marketplace.json`, root package.json `dev:cli:marketplace`).
- **Sessions/persistence**: JSONL event wire under `~/.kimi-code/sessions/wd_<slug>/<sessionId>/` plus `session_index.jsonl` [doc: data-locations.md:29-73, consistent with code]. Wire protocol is versioned (`V2_WIRE_PROTOCOL_VERSION = '1.5'`) with typed records (`turn.prompt`, `llm.request`, `context.apply_compaction`, `context.undo`, …) and in-place migrations (`human/persist/v2/wire.ts:7-48`, `migrate.ts`). Resume = replay + machine refold; undo and fork are first-class (`agent/undo`, `context.undo` record, session fork prints a ready `kimi --resume` command [doc: sessions.md:90]).
- **Storage layers below the core**: `minidb` is a pure-Node embedded KV store (in-memory Redis-style + SQLite-style WAL/snapshot durability, minidb/package.json description) backing kap-server-side state; `transcript` is an isomorphic render data layer (L1 agent-granular store, idempotent L2 ops, granularity-gated L3 subscriptions) shared by TUI/web/vscode; `telemetry` is shared OTLP-style infra; `migration-legacy` migrates the *previous* kimi-cli data dir. A legacy v1→v2 session converter lives beside the wire (`persist/v2/convert.ts`, `migration` in session dir).

## 2. Key techniques (source-verified)

**Tool execution: declared-access scheduling.** Tools declare read/write file access (`ToolAccesses`: `{kind:'file',operation,path,recursive}` or `{kind:'all'}`); a conflict-aware scheduler runs non-conflicting calls concurrently and serializes conflicts (file-vs-file overlap, anything-vs-`all`) with FIFO queues (`toolExecutor/toolScheduler.ts:21-88`; contract `tool/toolContract.ts:126-192`). This is exactly what crush's boolean parallel flag cannot do, and what Zero Code's registry lacks. A duplicate-call dedupe layer sits alongside (`agent/toolDedupe/`).
**Tool-set scaling: deferred tools.** `select-tools` implements progressive disclosure: most tools ship schema-less ("deferred"), the model loads them at runtime by name; the loader tracks already-available, policy-denied, stale-loaded, unknown names plus escalation counts and consecutive-failure backoff (`toolSelect/toolSelect.ts:7-40`, `toolSelectService.ts`, dynamic tool announcements in `toolSelectAnnouncements`). Same design point as Zero Code's `tool_search`/`tool_exec`, but with schema loading rather than call proxying.
**Subagents and the swarm (verified).**
- `agent` tool: zero-context or **forked** subagents (snapshot of parent history, inherits tools/model), background mode gated by capability files (`tools/agent/agent-fork.md`, `agent-background-enabled.md`); background work tracked by `task-list/task-output/task-stop/task-wait` tools (`tools/task/`).
- `agent-swarm` (feature flag, `features/swarm/`): map-reduce over up to **128 subagents** (`MAX_AGENT_SWARM_SUBAGENTS`, `agent-swarm/agent-swarm.ts:7`) driven by a `prompt_template` with an `{{item}}` placeholder — each list item spawns one subagent.
- Swarm follow-ups are first-class: `resume_agent_ids` maps previous subagent IDs to fresh prompts (resumed members keep their original agent type and model and launch before new item spawns); `fork: true` gives every item a parent-context snapshot; per-swarm model override chooses any catalog alias or "primary" (`agent-swarm.ts:12-57`).
**Permissions as a policy chain.** Ordered named policies, each a small file: `user-configured-deny/ask/allow` → `dangerous-command-ask` → `git-control-path-access-ask` → `sensitive-file-access-ask` → auto/yolo modes → `fallback-ask`, with session approval memory (`permissionPolicy/policies/`, 14 files). Dangerous-command verdicts come from a **tree-sitter-bash parse** (`app/bashParser/bashParserService.ts` imports the repo's `tree-sitter-bash` package; consumed at `dangerous-command-ask.ts:117-142`) — the same technique as Zero Code's tree-sitter bash permissions. Bash targets are even parsed to decide which path-scoped AGENTS.md apply (`agentsMdReminder/bashTargets.ts`).
**AGENTS.md done lazily.** Instead of concatenating all rule files, a reminder service injects only the AGENTS.md files that apply to paths *touched by recent tool calls*, as a mid-conversation reminder ("apply to paths accessed by your recent tool call, but were not included in your system prompt"), plus a changed-on-disk detector after injection (`agentsMdReminderService.ts:355, 363`). Config/skills/AGENTS.md hot-reload is now opt-in (`KIMI_CODE_WATCH=1`) [doc: .agents/skills/gen-changesets quotes the changeset wording].
**Edit + bash models.** `edit` is strict exact-match with aggressive prompt-level discipline: read-before-edit mandatory, *no consecutive same-file edits* (stale `old_string` invalidation is named in the tool description), a write lock serializes same-file edits in response order, CRLF/LF view mapping (`tools/edit/edit.md`). Bash spawns a fresh `$SHELL -c` per call with cwd resolved from the session working-dir view; long-running processes become tasks managed via `task-*` tools (`os/bash/bashTool.ts:146-202`, `process-task.ts`).
**Compaction (256k-window management).**
- Default strategy: trigger/block at **85%** of the window with a **50k reserved** budget, keep the newest ≥4 messages capped at 20% of window, overflow path retries up to 3 times requiring ≥5% reduction each (`fullCompaction/strategy.ts:7-27`).
- `checkAfterStep` is enabled whenever trigger≠block, so a single giant tool result compacts mid-turn instead of after the next overflow error (strategy.ts:62-64); window source prefers `max_input_tokens` over raw context size (strategy.ts:80-83).
- The compaction prompt is a *handoff brief* written for the next model: preserve the real ask (long pastes are truncated in kept messages), settled-vs-open decisions, exact commands with returned values, final code only, name unknowns, and invest in the forward plan since "the next turn resumes with less" (`fullCompaction/compaction-instruction.md`).
- Supporting machinery: `contextMemory` folds loop events, repairs open tool exchanges, strips vacuous content (`contextMemory/openToolExchange.ts`, `vacuousContent.ts`); `contextRecovery.ts` + footer prompt handle provider-side context-overflow errors as a `proposeRecovery` strategy invoked from the turn machine (turn.ts:620-660).
**Recovery/retry inside a step.** LLM remote failures evaluate a recovery proposal first (e.g. credential refresh, context recovery), rolling back the streamed accumulator and re-entering `thinking` with the proposal recorded; otherwise exponential retry with `Retry-After` respect (`turn.ts:614-704`); aborted streams *salvage* partial content (`salvageAborted`, turn.ts:710). Tool calls detached mid-run become async-ack tool results so the turn can settle without the tool (machine.ts:831-848; `asyncAckOutcome` turn.ts:756-770).

**Model-specific tuning for Moonshot/K2 (the "own-model harness" thesis).**
- Kimi thinking wire: `thinking: {type: enabled|disabled, effort, keep}` with `preserveThinking` when `keep === 'all'` (interleaved thinking retention), strict thinking validation, `max_completion_tokens`, and **auto-sized completion budget = context window − estimated used context tokens** when unset — computed from a per-request token estimate (`llm-kimi/trait.ts:83-105, 73-79`; estimate fed in at turn.ts:497-505 via `estimateUsedContextTokens`).
- Wire quirks handled at the trait layer: empty assistant `content` is *deleted* when tool_calls are present (K2 rejects empty-string content, trait.ts:122-131); tools may ride on the system message (trait.ts:133-135); `extras` preserved per tool-call for round-tripping (trait.ts:137-150); usage read falls back to `choices[0].usage` (trait.ts:152-161); `$`-prefixed tools become `builtin_function` server-side tools (trait.ts:53-56); `prompt_cache_key` passthrough (:86); tool JSON-Schemas are fully deref'd, `$defs`/`definitions` stripped, and missing `type` slots completed before send (`llm-kimi/schema.ts:4-60`, `normalizeKimiToolSchema`).
- Kosong (the public adapter pkg) additionally carries `merge-user-messages.ts` (merge consecutive user messages — a known K2 serving requirement), `tool-call-id.ts` + core's `toolCallIdNormalizer.ts` (84 lines, seeds IDs from history to keep call IDs coherent across requests), and `reasoning-key.ts`; a capability registry gates which quirks apply per endpoint (`kosong/src/providers/`).
- Thinking policy is model-metadata-driven: per-model `supportEfforts`, `defaultEffort`, `offEffort`, `alwaysThinking`, `adaptiveThinking`, with typed config errors instead of silent drops (`human/llm/thinking.ts:9-49`).
- All of that metadata is machine-readable, not hard-coded: the core consumes a models.dev-style remote catalog and maps each entry into `maxContextSize`, `maxInputSize` (capped at context), reasoning effort ladder, `interleaved → reasoningKey`, and per-modality capability flags (`human/models-dev/models-dev.ts:175-195`). K2's 256k window, effort ladder, and interleaved-thinking support arrive as data — adding a new Moonshot model is a catalog edit, not a code change.
**Delivery vocabulary (steer vs queue) is explicit and machine-encoded.**
- Prompt submission goes through a channel with per-prompt handles and completion futures (`loop/promptChannel.ts`); prompts entering the queue can be canceled per-seq and dropped with a terminal event before ever running.
- Queued prompts are drained only at safe boundaries via the machine's `turn.drain`, which injects notifications+reminders into the turn's `draining` state (machine.ts:821-827, turn.ts:812-856); promoting new input resets the step counter (turn.ts:849-855).
- An explicit steer targets prompt IDs (`loopService.ts:364`) and emits a `promptSteered` journal event; incoming prompts can be blocked by a pluggable gate (`runPromptGate`, loopService.ts:572; `promptBlocked`/`promptGateFailed` machine events).
- Net effect: Zero Code's documented V2 steer/queue algebra, but live, journaled, and exercised by every session.
**Observability is wired to the loop.** Every step carries an `LLMRequestTrace` + `ModelRequestTiming` through machine events (engine.ts:3-4, `stepCompleted.timing`), retry/recovery transitions are first-class emitted events with attempt counts and delays (engine.ts:79-101), and `llm-adapter/record-diff.ts` diffs request records for inspection; `apps/kimi-inspect` and `apps/vis` consume this — decoded wire vs machine fold can be inspected per session.
- The decode-vs-consume split is *durable*, not just live: each step's `step.end` journal record persists `llmFirstTokenLatencyMs`, `llmServerFirstTokenMs`, `llmServerDecodeMs`, `llmClientConsumeMs`, `llmClientBlockedMs` (loopService.ts:1817-1823) — Zero Code computes an engine-decode vs observed-decode delta in its ledger but nothing per-step in the transcript consumes it; here it's part of the session record itself.
- Durable projection writes are serialized on a per-turn promise chain (`turn.afterChain`, loopService.ts:1798, 1836-1845) so machine events and history-store appends can't interleave out of order.
- Tool calls that reference names not loaded for the current step (deferred/stale via `select_tools`) are still executed through the normal executor path and settled with a durable tool result (loopService.ts:1528, 1651-1695) — a hallucinated or stale tool name can never leave a dangling `tool_calls` entry in the durable history.

**Remote control / multi-device (head-commit area).**
- `kimi rc`/`kimi web --remote-control` registers a device tunnel to the hosted relay `https://code-rc.kimi.com` (`remote-control/remote-control.ts:21`) over WebSocket, relaying HTTP to the loopback kap-server with header allow/deny lists (blocking hop-by-hop and identity headers, :36-57), gzip for compressible bodies (:58-64), 30 s pings with a 300 s silence timeout (:40-42), 10 MB request / 64 KB header caps (:33-35), and a single-instance lock file per machine (`remote-control/lock.ts`, `manager.ts`). Device identity comes from the OAuth login (`createKimiDeviceId`); the printed link + QR code grants control to whoever holds it, and same-account login is required server-side [doc: docs/en/guides/remote-control.md].
- kap-server's `remoteControl` route set is status/enable/list/rename/**delete** — the head commit adds `DELETE` with coordination against the local tunnel when deleting *this* machine's device (routes/remoteControl.ts:22-27 + commit message). ~3-device account limit, paid-membership gate, machine-awake requirement [doc: remote-control.md].
- Device lifecycle details worth noting: `createKimiDeviceId` derives stable device identity from the OAuth account; a per-machine lock file prevents double-registration and the second instance reports the live instance's link instead of failing opaquely (`remote-control.ts:96-99`, `lock.ts`, `RemoteControlAlreadyRunningError` surfaced as a typed API error envelope with already-running details, routes/remoteControl.ts:29).
- Execution always stays local: "the web page is just a remote window" [doc]; approvals/questions are ordinary durable API resources (`routes/approvals.ts`, `questions.ts`), so any client can answer them — the same multi-client prompt problem crush's head commit fixed by SSE filtering, solved here by server-routed approvals.
- The relay client is deliberately *dumb transport*: only HTTP/WS bytes cross it; header filtering happens in the client itself (relay request headers `authorization`/`cookie`/`host` are blocked so relayed traffic can't smuggle identity, `remote-control.ts:36-47`), and all agent-side auth is kap-server middleware that treats `/api/*` uniformly (`kap-server/src/middleware/auth.ts:43`). No agent logic crosses the relay.

## 3. Strengths

1. The only audited harness where control flow is a *typed, inspectable state machine* with a durable event journal: pause/continue/abort/steer/detach/retry/recover are all machine events, restore = replay+refold. Every failure mode seen in other audits ("crash mid-drain", "lost steer") is an event here.
2. Conflict-aware parallel tool execution from declared file accesses — strictly better than both crush's static flag and Zero Code's serial default.
3. The K2 trait layer is the most complete example of model-specific wire tuning found in any audit: empty-content deletion, schema deref, completion-budget auto-sizing, builtin tools, thinking `keep`, call-ID normalization — all as small declarative hooks on generic OpenAI/Anthropic bases.
4. Compaction engineering is best-in-class alongside Claude Code: ratio+reserve+recent-tail policy, mid-step trigger, overflow-reduction floor, and a handoff prompt explicitly designed around what the *resuming* model can and cannot re-derive.
5. Lazy, path-scoped AGENTS.md injection beats whole-prompt rule stuffing on token cost and relevance; tree-sitter-bash supplies the path targets.
6. Permission policy chain is data (14 small named policies, ordered) rather than a monolithic checker, and reuses the bash parser for verdicts.
7. Abort semantics are layered and bounded: abort sets a machine-level `aborting` substate with a *timeout* to force-stop tool actors that ignore cancellation (machine.ts:920-933), a grace period inside `acting` for in-flight tools (turn.ts:803-818), and partial-output salvage on LLM abort (turn.ts:710) — no path can wedge a turn indefinitely.

## 4. Weaknesses

1. Sheer stack depth: agent machine + turn machine + tool actors + loopService wrapper + event-store mirror + two parallel adapter stacks (kosong vs human/llm). The `MachineEngineEvent` vocabulary is a ~25-case contract that every surface (TUI, kap-server, vis, transcript) must track; onboarding cost is high and the vendored `src/human` core duplicates concepts its sibling package `kosong` already owns.
2. Remote control trust model is thin by design: bearer-link control ("anyone who has it may control your sessions and files" [doc]) and a loopback-only assumption; there is no per-session authorization granularity.
3. Swarm's 128-subagent ceiling and per-item model overrides have no visible per-swarm budget/cost accounting in the tool contract — cost control is prompt-level advice [doc].
4. Bash is one-shot per call: no persistent session state (env/cd), and no sandbox claim — isolation of dangerous commands is permission-gating, not execution containment.
5. Exact-match edit + prompt discipline pushes all matcher burden onto model compliance; weaker models will burn more read/edit cycles than under Zero Code's cascade.
6. The wire/journal format has already had ≥5 protocol revisions (1.0→1.5 migrations in one file) — event-sourcing churn cost is visibly being paid in migration code.
7. The repo is a v2 rewrite mid-flight: `agent-core-v2` plus `migration-legacy` (old `~/.kimi/` → `~/.kimi-code/`) plus a v1 session converter inside v2's own persistence module — Moonshot has paid the "rewrite the harness once" cost that Zero Code's Option-B-vs-D decision is weighing, and still ships two wire generations.
8. No LSP story at all: repo intelligence is grep/glob/read plus tree-sitter-bash only — the weakest code-navigation surface among the top-tier audited harnesses, leaning entirely on K2's long-window retrieval habits.

## 5. Works vs unproven

- **Source-verified working**: state-machine loop with steer/detach/abort-timeout; conflict scheduler; deferred-tool `select_tools`; fork/background subagents; swarm tool contract incl. resume map; compaction strategy + handoff instruction; tree-sitter-bash permission verdicts; K2 traits and schema normalization; versioned JSONL session wire; device tunnel client with request-header blocklist (authorization/cookie/host stripped) per remote-control.ts:36-47; device delete route (head commit).
- **Test surface**: vitest suites sit beside every module including the vendored core (`src/human/test/` — machine, tool-select recovery strings, etc.); CI-style publish gate chains `typecheck`+`lint`+`sherif`+`test`+`publint` (root package.json `publish`).
- **Documented-only**: device link security posture and limits, paid gate, ~3-device cap [doc]; QR/UX flows [doc]; `kimi web` local UI details; hot-reload opt-in flip (changeset text).
- **Documented in docs tree**: bilingual docs site (`docs/en|zh`) covering sessions, remote control, providers, overrides — the [doc]-tagged items above were read from it, not from binaries.
- **Unproven in-repo**: swarm end-to-end quality (no budget accounting visible); compaction measured impact (no cache-hit/quality telemetry published); restore-refold under partial-journal corruption (migrations exist, but recovery semantics not asserted).

## 6. What Zero Code should learn

1. **Declared file/path accesses per tool → conflict-aware scheduler.** One small interface (`{files} | {all}`) plus the 90-line scheduler replaces the "all tools serial unless flagged" model and directly enables safe parallel Edit/Read batches; pair it with kimi's same-file write-lock rule from `edit.md`.
2. **Completion-budget auto-sizing for local models**: compute `max_completion_tokens = window − estimated_context_used` when the caller doesn't set one (`kimiUnsetCompletionTokens`); Zero Code already estimates context for compaction — reuse it to stop self-truncation on long local runs.
3. **Model quirk traits over per-provider forks.** Express provider/model quirks as typed hooks on a generic wire builder (empty-content deletion, schema deref, usage fallback location, thinking kwargs) — the pattern any local-model harness (including mlx-served K2/qwen builds) needs; Zero Code's provider handling should follow the trait shape, not its specifics.
4. **Adopt the handoff-summary framing for compaction**: the instruction's "preserve the ask, separate settled from open, name unknowns, commit the forward plan now" beats section-templated summaries and Zero Code's cache-continuation summaries can adopt the same content contract at no cache cost.
5. **Path-scoped lazy AGENTS.md reminders** (which rules apply to files you *just touched*, plus change-after-injection detection) is a cheap, cache-friendly complement to Zero Code's frozen system prefix — inject as stable-index pressure notes rather than prompt-prefix churn.
6. **Policy-chain permissions** with a tree-sitter-bash verdict feeding ordered named policies — Zero Code already parses bash with tree-sitter; reshaping the checker into an ordered policy list would make user overrides (allow/ask/deny rules) composable without special-casing.
7. **Durable prompt/answer resources for interactive prompts** (approvals/questions as server-side objects any client can answer) is the cleaner V2 design for Zero Code's clustered-execution future — better than crush's stream-filter hack because answering is idempotent and auditable.
8. **Never leave a dangling tool-call.** Execute unresolvable/stale tool names through the normal result path so every emitted `tool_call` gets a settled, durable tool result — this invariant is what makes Zero Code's durable-history reload-after-crash safe; kimi additionally serializes durable projections on one per-turn chain (`turn.afterChain`) so event order and store order can't diverge.
9. **Persist decode telemetry per step, not just per session.** Kimi's `step.end` record (first-token, server first-token, server decode, client consume, client blocked) is exactly the per-component breakdown baseline finding #7 says Zero Code lacks — and it's cheap because it lands in the journal the step already writes.
10. **Don't stuff AGENTS.md.** Path-scoped lazy reminders over Zero Code's existing stable-index pressure-note mechanism would cut system-prompt tokens for large monorepos without breaking prefix caches (rules injected mid-conversation don't perturb the frozen prefix).
11. **On the "harness tuned to its own model" thesis:** kimi demonstrates the achievable ceiling — model quirks expressed as small declarative traits + a remote capability catalog, so tuning scales to every Moonshot model without loop changes; and it also shows the ceiling's limit: tuning buys reliability and token efficiency, not repo intelligence (still grep-only). Zero Code's equivalent play is trait-ized adapters for its local/K2-class models **plus** keeping the LSP bet (crush §6.1), since model tuning alone leaves the retrieval floor low.
