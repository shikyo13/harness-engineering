# 02 — Competitor audit: OpenAI Codex CLI (codex-rs)

Repo: `Datasets/harness-research/repos/codex`, head `6786dccbe7261b75103260475bc0a04cb36c2c0a` (2026-10-13, branch `main`; only `main` fetched — no dev branches visible locally).
Method: direct source reading of `codex-rs/` (~90 crates). All `file:line` paths are relative to `codex-rs/`. Claims tagged **[V]** = source-verified, **[D]** = documented-only.

**Scope note:** this head is far larger than the codex most people describe from memory: realtime WebRTC voice, a Windows MXC sandbox, "Guardian" automated approval review, an agent message board / graph store, code-mode (V8 tool runtime), hooks, plugins/apps/connectors/skills, cloud tasks, worktrees, rollout trace bundles. The classic spine (protocol → session → turn loop → sandboxed exec → apply_patch → rollout JSONL → compaction) is still intact and is the audit focus.

## 1. Architecture

Layered workspace, dependency flow roughly `protocol` (wire types only) → `core` (orchestration) → surfaces (`tui`, `exec`, `app-server`, `cli`). Notable crates: `protocol`, `core` (~5500-line `session/mod.rs`), `sandboxing`, `execpolicy`, `apply-patch`, `rmcp-client` (MCP), `rollout` + `history` + `thread-store`, `models-manager`, `prompts`, `network-proxy`, `rollout-trace`, `windows-sandbox-rs`/`-service`, `agent-graph-store`/`agent-roles`/`agent-message-board-client`, `code-mode-*`, `linux-sandbox`, `bwrap` (vendored) [V].

- **Wire protocol is the trunk.** `Op` (client→agent submissions) and `Event{ id, msg: EventMsg }` (agent→client) are a versioned serde/TS-schema'd enum; every `Op` carries a `oneshot` reply channel when it needs an answer (`protocol/src/protocol.rs:653` — `Interrupt`, `TurnInput`, `RecoverTurn`, `SuspendTurnAndShutdown`, `ThreadSettings`, `TurnSettings`, `ExecApproval`, `InterAgentCommunication`, realtime ops). `EventMsg` carries correlation `id` = submission id (`protocol.rs:1449-1467`); `TurnStarted`/`TurnComplete` serialize as legacy `task_started`/`task_complete` with alias for v2 interop (`protocol.rs:1516-1528`) — wire stability is treated as a durable API.
- **Session = actor over submission channel.** `Session` (`core/src/session/session.rs`, 2004 lines) owns state (mutex'd `state::Session`), history, model client, input queue; a run loop dispatches `Op`s. Tasks implement a `SessionTask` trait with `TaskKind` (`core/src/tasks/mod.rs`; `RegularTask`, `ReviewTask`, `CompactTask`, `UserShellTask`) — one active task per session, child `CancellationToken`s per turn.
- **Turn loop.** `RegularTask::run` (`core/src/tasks/regular.rs:41-125`): emit `TurnStarted` inline (first-token latency not gated on prewarm), then `loop { run_turn(...) }` re-runs while `input_queue.has_pending_input` — steering input that arrived mid-turn re-enters the loop instead of a new task. `run_turn` (`core/src/session/turn.rs:166`): pre-turn auto-compaction check → record inputs durably → capture an immutable `StepContext` (context + tool router + settings snapshot, `turn.rs:262`) → sampling loop. Each iteration drains pending input into history (`turn.rs:441`), rebuilds `StepContext` if input changed, builds request from `sess.clone_history().for_prompt(...)` (`turn.rs:536`), calls `run_sampling_request`.
- **Streaming settle + parallel tools.** `try_run_sampling_request` (`turn.rs:2567`) consumes the provider stream; each completed `ResponseItem` goes through `handle_output_item_done`, which returns an optional tool future pushed into `FuturesOrdered` (`turn.rs:2634, 2854`); the stream keeps being consumed while tools run, and `drain_in_flight` settles them before the step ends (`turn.rs:2514, 3229`). Parallelism is opt-in per tool: `ToolCallRuntime` holds one `Arc<RwLock<()>>`; parallel-capable tools take the **read** lock, mutating tools take the **write** lock (`core/src/tools/parallel.rs:46-51, 140, 213-216`); registry exposes `supports_parallel_tool_calls` (`tools/registry.rs:606`). AbortOnDropHandle + per-call cancellation with `finishes_on_cancellation` opt-out for tools that must complete (e.g., durable writes).
- **Turn boundaries + observability.** One turn = one task run = many provider steps. `TurnStarted` at task start; `TurnComplete` emitted by the task harness (`core/src/tasks/mod.rs:865`) with last agent message + usage. `TurnDiffTracker` accumulates the whole turn's file diff (lifecycle of a task, displayed per turn — comment at `turn.rs:422-425`). `TokenCount` events carry optional totals/last-turn usage with an explicit "UIs must not display None" contract (`protocol.rs:1533-1536`). Sampling is instrumented end-to-end: OTel spans plus a `feedback_tags!` blob capturing model/approval/sandbox/effort/auth-mode per request (`turn.rs:2579-2590`) and `turn_timing_state` phase timing incl. tools-change detection (`turn.rs:2596-2599`). Startup is prewarmed speculatively and *consumed* by the first regular turn (`tasks/regular.rs:70-81`, `session/startup_prewarm.rs`). `Interrupt` deliberately does **not** kill background terminals — interruption semantics are split between turn death and process death (`protocol.rs:657-671`).

- **Entry plumbing.** `Session` is built behind a bounded `async_channel::bounded(512)` submission pair (`core/src/session/mod.rs:554,644` — `SUBMISSION_CHANNEL_CAPACITY`), so a chatty client backpressures instead of buffering unbounded work; `SessionIo` exposes the typed sub/event halves and is the *same* interface a sub-agent delegate uses (§6) — surfaces (TUI, `codex exec`, app-server, MCP host, realtime) are thin translators over `Op`/`Event`, with `app-server-transport` adding its own channel capacity layer for the daemon protocol.

### Crate map and invariants (observed import directions)

`protocol` (pure types: Op/Event/items/permissions/sandbox enums) ← `history` (RolloutItem) + `rollout` (storage) ← `core`; `sandboxing` depends on protocol + network-proxy but not on core (usable by `exec-server` alone); `execpolicy` is standalone with its own CLI; `apply-patch` is a library *and* a standalone binary (`apply-patch/src/standalone_executable.rs`) so patches can be applied from inside another sandbox. Surfaces (`tui`, `exec`, `app-server`, MCP host, realtime) speak `Op`/`Event` and do not reach into core internals. This dependency discipline is the reason a 90-crate fork still builds one coherent loop. [V]

## 2. Sandbox & execution infrastructure

- **Two orthogonal axes:** `AskForApproval` (UnlessTrusted / OnRequest / Granular{sandbox_approval, rules, skill_approval, request_permissions, mcp_elicitations} / Never — `protocol/src/protocol.rs:1095-1156`) and `SandboxPolicy` (danger-full-access / read-only / workspace-write{writable_roots, network_access, exclude_tmpdir, exclude_slash_tmp} / external-sandbox — `protocol.rs:1181-1235`). Network is a first-class field (`NetworkAccess::Restricted|Enabled`, `protocol.rs:1165`).
- **Platform enforcement:** `SandboxType = None | MacosSeatbelt | LinuxSeccomp | WindowsRestrictedToken | WindowsMxc` (`protocol/src/sandbox.rs:29`). macOS: only `/usr/bin/sandbox-exec` is trusted (PATH-injection defense, `sandboxing/src/seatbelt.rs:60`); base profile is `(deny default)`-first, Chrome-inspired (`seatbelt_base_policy.sbpl:1-10`); network is separately layered (`seatbelt_network_policy.sbpl`) with loopback-proxy-port allowlists derived from env (`seatbelt.rs:76-110`) and a managed MITM CA readable-root injection for corporate proxies (`sandboxing/src/manager.rs:66`). Writable roots carry **read-only subpaths + protected metadata names** so the agent cannot touch `.git/hooks`, `.codex` under a writable root (`protocol.rs:1237-1260`, regex generation at `seatbelt.rs:592`). Linux: landlock/seccomp + bubblewrap + PID namespace variants (`sandboxing/src/landlock.rs`, `bwrap.rs`, `linux_pid_namespace.rs`); Windows: restricted-token and MXC AppContainer-style stacks (`windows-sandbox-rs/src/acl.rs`, `app_package.rs`, `windows_mxc.rs`) — the Windows story is much deeper than upstream's was [V].
- **Denial → escalation, not guesswork.** After a sandboxed run, output is classified: `is_likely_sandbox_denied` → `SandboxErr::Denied` recorded with violation evidence (`core/src/exec.rs:828-835`); approval escalation then either re-runs unsandboxed or *keeps* the sandbox when the denial involved protected reads (`core/src/tools/sandboxing.rs:287-316`). The model can also self-request escalation (`requires_escalated_permissions`), and only an explicit user approval widens the filesystem (`sandboxing.rs:255-258`).
- **execpolicy DSL.** Starlark-flavored `prefix_rule(pattern=["git", ["pull","push"]], decision="allow|prompt|forbidden", justification=..., match=..., not_match=...)` + `host_executable(name, paths)` pinning which absolute paths may resolve through basename rules; `match`/`not_match` are load-time unit tests; a `network_rule` exists too (`execpolicy/src/decision.rs:9-27`, `parser.rs:349-410`, README examples; CLI `codex execpolicy check --rules x.rules git status`). Decisions are ordered: Forbidden > Prompt > Allow, default allow for covered prefixes.
- **Network approvals are their own flow:** a denied outbound connection routes through `tools/network_approval.rs` (network denials become approval requests with policy decisions attached to `SandboxErr::Denied.network_policy_decision`, `exec.rs:832`), and effective permissions are computed as an *intersection* of stacked permission profiles (`protocol/src/permission_profile_intersection.rs`, `permission_profile_snapshot.rs`) rather than last-writer-wins. [V — intersection model verified by module existence + snapshot types; per-layer precedence details not traced line-by-line]
- **Prompt vs mechanism.** The system prompt does *not* beg the model to be careful; templates merely describe the enforced state ("`sandbox_mode` is `workspace-write`: ... Editing files in other directories requires approval", `prompts/templates/permissions/sandbox_mode/workspace_write.md`) and adjust test-running etiquette per approval mode (`base_instructions/default.md:161-163`). Enforcement is OS-level; the prompt is a *description of the mechanism*. [V, strong]
- **Unified exec / persistent shell.** `unified_exec` is a persistent PTY process manager: up to 64 concurrent processes (`core/src/unified_exec/mod.rs:77`), yield-window clamped 250 ms–30 s (`:68-72`), stdin writes to live processes, head+tail output buffer (`head_tail_buffer.rs`), per-session shell snapshots for env fidelity (`shell_snapshot.rs`, 1210 lines) with prewarm speculation after hooks accept a turn (`turn.rs:611-618`). Output is capped hard: 1 MiB aggregated per exec call (`core/src/exec.rs:58,81` via `DEFAULT_OUTPUT_BYTES_CAP`, `utils/pty/src/lib.rs:25`), ≤10 000 streamed deltas per call (`exec.rs:85`), aggregation reserves 1/3 stdout / 2/3 stderr under contention, rebalancing (`exec.rs:883-905`). Truncation happens at capture time, so what the model sees is what the rollout records.

## 3. apply_patch

- **Format** unchanged lineage from the Zero-known form: `*** Begin Patch` / `*** Add File: p` (+lines) / `*** Delete File: p` / `*** Update File: p` with `@@` context hunks and optional move (`*** Move File:` handled in parser hunks) (`apply-patch/src/parser.rs:12-41`); heredoc-wrapped shell form still accepted (`invocation.rs:164-183`). Model-facing tool type is per-model metadata: `apply_patch_tool_type: "freeform"` in `models-manager/models.json` (function vs freeform/custom tool).
- **Matching is forgiving by design:** `seek_sequence` tries exact, then trailing-whitespace-insensitive, then both-ends-trim, and when a hunk is EOF-anchored searches from the end first (`apply-patch/src/seek_sequence.rs:1-40`); pattern-longer-than-file early-returns (documented past panic fix). New file content derived in-memory per chunk before any write (`file_update.rs:25-60`); a unified diff is generated purely for display/events (`file_update.rs:176`). Parent-directory-missing write retry exists (`lib.rs:765`).
- **Apply goes through the same safety gate as exec:** `assess_patch_safety` → `AutoApprove | AskUser | Reject{reason}` against the effective filesystem policy, distinguishing executor-managed vs platform-sandbox routes (`core/src/safety.rs:19-67`). So a patch *outside* the sandbox roots becomes an approval prompt, not a silent write.
- **Streaming parser** (924 lines, `streaming_parser.rs`) incrementally parses the patch *while the model is still emitting it* and streams a live diff to the UI via `ToolArgumentDiffConsumer` (`turn.rs:2638-2640, parallel.rs:68-75`). The model's tokens double as the diff preview.

## 4. Context engineering

- **Base instructions:** 275-line `protocol/src/prompts/base_instructions/default.md` (personality, AGENTS.md spec, preamble etiquette, sandbox/approval section, planning). Per-model override via `models.json` templates compiled into `ModelInfo.base_instructions` (`models-manager/src/manager.rs:888-927`), and **the session's exact base instructions are persisted into `SessionMeta`** for faithful resume (`protocol/src/protocol.rs:3248-3300`).
- **Model metadata discipline:** single `models.json` + `ModelsManager` with cache/identity (`models-manager/src/cache.rs`); `ModelInfo` carries slug, visibility, `truncation_policy {mode: bytes|tokens, limit}` (default 10 000 for tool outputs), `context_window`/`max_context_window`, `effective_context_window_percent` (default 90 %; `protocol/src/openai_models.rs:393,452-471`), `usable_context_window()` math (`:523-532`), `comp_hash` (context-affecting config hash — model switch + comp_hash change forces compaction, `turn.rs:1374`), `supports_parallel_tool_calls`, `use_responses_lite`, `multi_agent_version`, `tool_mode: code_mode_only`, input modalities. Zero's "model table" instinct is exactly this pattern, but Codex makes it the *only* source of model behavior and versions it in JSON.
- **Compaction is a subsystem, not a function call.** Trigger: `context_window_token_status` computes buffered auto-compact limit, full-window limit, post-turn percent threshold (`core/src/session/context_window.rs:84-126`); phases PreTurn/MidTurn/PostTurn/StandaloneTurn (`turn.rs:1322,1456,735`). Three engines behind one `run_auto_compact` dispatcher: (a) local summarize with a 9-line "CONTEXT CHECKPOINT COMPACTION ... handoff summary" prompt (`prompts/templates/compact/prompt.md`) and a `SUMMARY_PREFIX`-tagged summary re-injected into a rebuilt history that also re-materializes **initial context + WorldState baseline** (`core/src/compact.rs:87-106, 393-404`); (b) **remote compaction V2** — server-side compaction with foreground fallback and image-budget handling (`compact_remote_v2.rs`, 1353 lines); (c) TokenBudget experimental path that *resets* the window with history-notes (`session/token_budget.rs`, `compact_token_budget.rs`). `ContextCompacted` is a persisted event so replay matches what the model saw.
- **Context assembly:** per-step immutable `StepContext` = settings + world state + tool router, captured once and shared by request building and tool dispatch (comment `turn.rs:261`); world state changes recorded as diffs (`record_step_world_state_if_changed`, `turn.rs:515`; `core/src/context/world_state`), plus dozens of typed context fragments (`core/src/context/*.rs`: time reminders, token-budget context, turn-aborted notices, model-switch instructions...). AGENTS.md is merged from root→CWD at spawn with documented precedence rules (`default.md:18-28`, `agents_md.rs`).

- **Prompt-engineering details worth noting:** the base prompt operationalizes UX, not capability — "preamble messages" spec (group related actions, 8–12-word updates, no preamble for trivial reads; `default.md:31-38`), personality/tone block, approval-mode-specific test-running etiquette (`:161-163`), and proactive-next-step phrasing (`:189`). Plan mode gets its own streaming pipeline: assistant text is parsed per-segment into plan items with a dedicated `update_plan` tool (`turn.rs:2236-2512`, `tools/handlers/plan_spec.rs`), and reasoning-summary section breaks are surfaced as typed events (`EventMsg::AgentReasoningSectionBreak`), with a `ConcurrentReasoningSummaries` feature gate choosing sequential-cutoff rendering for OpenAI models (`turn.rs:2606-2611`).
- **Background compaction + async surfaces:** `run_auto_compact` accepts a `BackgroundCompactionCandidate` and can install a pre-computed compaction when the limit hits instead of blocking the next request (`turn.rs:1463,1500-1530`, `session/async_compaction.rs`); async tool handlers exist for `sleep`, `wait_for_environment`, `request_user_input_async`, `send_message_to_user_async` (`core/src/tools/handlers/*_async*`), and `session/turn_suspension.rs` lets a turn park on an external wait.
- **Sidecar history stores:** attachments (`attachment-store` crate), cross-session user message history (`message-history`), and long-term memory with model-visible citations (`memories` crate, `protocol/src/memory_citation.rs`) sit beside rollouts rather than inside them; `RetainedContext` items keep post-compaction survivors inside the rollout while bulky payloads stay external (`core/src/compact_retained_tool_outputs.rs`, `session/retained_context.rs`). [V — existence + wiring; depth of memory quality unassessed]

## 5. Sessions, rollouts, resume/fork

- **Rollout = append-only JSONL** at `~/.codex/sessions/YYYY/MM/DD/rollout-<ts>-<uuid>.jsonl` (`rollout/src/list.rs:422`), optional compression (`rollout/src/compression.rs`), SQLite index/state-DB overlay for listing/search (`state_db.rs`, `session_index.rs`, `reverse_jsonl_scanner.rs`). Line items are typed `RolloutItem`: `SessionMeta`, `ResponseItemEnvelope`, `Compacted`, `TurnContext`, `TokenUsageRecord`, `WorldState`, `RetainedContext`, `SecurityRiskScore`, `InterAgentCommunication`, `EventMsg`, `RealtimeItem` (`history/src/lib.rs:215-232`) with an explicit persist policy (`rollout/src/policy.rs:80-178` — reasoning/raw content, exec/patch/MCP/web-search ends, guardian assessments persist; deltas mostly don't).
- **Writer durability:** single writer task with pending queue, explicit `flush()` ack via oneshot, and *retry-after-failure* writer survival (`recorder.rs:1065, 1192, 1807-1824`); file lock per rollout (`writer_lock.rs`); deferred materialization (file created on first real content).
- **Resume/fork:** `RolloutRecorderParams::resume(path)`; `ThreadManager` reads via `thread-store` (`thread_manager.rs:1016`), reconstructs history including compaction windows and truncation (`session/rollout_reconstruction.rs`). `SessionMeta` records `session_id` (root thread), `id`, `forked_from_id`, `forked_from_ordinal_exclusive`, `history_base`, `agent_role/agent_path/nickname`, cwd, provider, base_instructions (`protocol.rs:3248-3300`). Forks copy persisted history (`ForkPersistence::Copied`) and support truncation at the last **sampling boundary** so a fork never inherits a half-finished turn (`thread_manager.rs:197-208`). `RecoverTurn` + `SuspendTurnAndShutdown` ops give crash/interrupt-resume at turn granularity (`protocol.rs:700-717`, `session/daemon_recovery.rs`).
- **Compaction re-injection on resume:** reconstruction keeps the last compaction summary + post-compaction items, so a resumed session sees what a live one saw; `comp_hash` mismatch forces fresh compaction rather than mixed-context sampling (`turn.rs:1374`).

## 6. Multi-agent

- **Collab tools, v1/v2:** `spawn_agent`, `send_input`, `send_message`, `followup_task` specs with model-inheritance guidance ("inherit your current model; set `model` only on explicit request") (`core/src/tools/handlers/multi_agents_spec.rs:17-163`), versioned per model via `multi_agent_version: v2` in `models.json`. Per-agent roles via `agent-roles` crate + `agent_role` in SessionMeta.
- **Sub-agents are real Codex sessions:** `codex_delegate.rs` spawns a full Session with its own submission/event channels and asserts "Delegates never request approvals" (`codex_delegate.rs:47-49`); their rollouts persist under the same tree with `SubAgentSource`/`agent_path`, and Collab lifecycle events (`CollabAgentSpawnEnd/InteractionEnd/WaitingEnd/CloseEnd/ResumeEnd`) are durable policy-persisted (`rollout/src/policy.rs:166-170`).
- **Message board + mailbox preemption:** `InterAgentCommunication` is a first-class `Op` that records durable agent history and may trigger a turn (`protocol.rs:755-766`); when a reviewer/commentary arrives, the live stream can be *preempted* to deliver mail before the next model request (`turn.rs:2818-2870`, `Feature::DeferMailboxPreemption`). Background: `tasks/` kinds + background terminal processes survive `Interrupt` but die on `CleanBackgroundTerminals` (`protocol.rs:659-671`).
- Separate graph-store crate (`agent-graph-store`) persists agent topology. Review mode is one-shot delegation: `ReviewTask` runs `run_codex_thread_one_shot` with a 95-line rubric (`core/src/tasks/review.rs:27`, `prompts/templates/review/rubric.md`) and structured findings formatting (`protocol/src/review_format.rs`).

## 7. MCP & tool-set philosophy

- **Client** = `rmcp-client` over the `rmcp` SDK: stdio (bounded fd policy, executor-process and in-process transports), streamable-HTTP with retry/redirect modes, full OAuth incl. dynamic client registration + loopback callback + refresh-mode handling, elicitation client service, enterprise auth (EMA) headers (`rmcp-client/src/rmcp_client.rs:402-965`, `stdio_server_launcher.rs`, `oauth.rs`, `streamable_http_retry.rs`). MCP tool calls have dedicated approval templates and analytics (`core/src/mcp_tool_approval_templates.rs`, `mcp_tool_call.rs`, 2516 lines).
- **Host-side plumbing** lives in `codex-mcp`: prepared call bindings, a model-visible tool catalog (`client_tool_catalog.rs`, `connection_manager::tool_is_model_visible`), MCP *event streams* as a first-class resource concept (`McpEventStream`, `McpEventDefinition` — server-initiated notifications modeled, not improvised), resource client caching keyed by auth, and elicitation routed through the same reviewer/approval machinery as exec (`elicitation_reviewer`, §8). Turn input declares which MCP servers it *requires*; those requirements flow through `required_mcp_servers_for_input` into the `StepContext` capture so a request's advertised tool set and its server startup are one atomic step (`turn.rs:239-272`), and MCP runtime invalidation/reprojection is serialized through a single publish gate (`session/mcp_refresh.rs:6-10`).
- **Philosophy: small core, deferred periphery.** The always-on toolset is roughly shell/unified_exec (+write_stdin), apply_patch, plan, view_image, request_user_input, request_permissions, current_time, web_search (hosted), collab tools, `tool_search`/`new_context_window`. MCP/plugin tools are **deferred** and discovered by BM25 `tool_search` over tool metadata, exposed "for the next model call" — with explicit instruction to use it instead of `list_mcp_resources` (`core/src/tools/handlers/tool_search_spec.rs:94`). Namespaced connector ids on tool listings (`rmcp_client.rs:382-393`). Model-gated extremes: `tool_mode: code_mode_only` (gpt-6-astra) exposes tools only through the V8 code-mode runtime, where tool calls come back tagged `ToolCallSource::CodeMode` and go through the same parallel runtime (`parallel.rs:71-73, 676`).

## 8. Distinctive mechanics

- **Guardian = model-as-approver.** Approval requests are hosted by a *deterministic engine* plus an isolated synchronous reviewer session with its own budget, evidence selection, checkpointing and warnings (`core/src/guardian/mod.rs:1-3` "Hosts approval decisions and the isolated synchronous reviewer... core enforces permissions and mandatory review requirements"; `session/guardian_checkpoint.rs`; `GuardianAssessment`/`GuardianWarning` events persisted). `ApprovalsReviewer` is a per-turn-settable setting (`Op::TurnSettings`, `protocol.rs:744`). This is the most notable architectural novelty at this head: the human-approval path is being wrapped by an LLM triage layer *with durable budget accounting*.
- **rollout-trace:** a separate trace-bundle format + reducer for semantic replay/viewing of rollouts, decoupled from core hot path (`rollout-trace/src/lib.rs:1-30`) — replay is reducer-based reconstruction, not byte-deterministic provider replay (no mock clock; provider nondeterminism stays outside).
- **Notification design:** config `notify = [argv...]` invoked with a JSON payload on stdin (e.g. `{"type":"agent-turn-complete","turn-id":...}`) — one hook, machine-readable, no per-event plumbing (`core/src/config/mod.rs:782-792`).
- **Sandbox tags / violation ledger:** filesystem sandbox violations recorded per run (`sandbox_tags.rs`, `exec.rs:830`) and a persisted `SecurityRiskScore` rollout item — risk data accumulates *inside* history.
- **Hooks:** user-configurable lifecycle hooks (SessionStart/Stop/prompt) with trust status and async result draining between turns (`protocol.rs:1691-1780`; `drain_async_hook_results`, `turn.rs:179`).
- **[D]** `docs/sandbox.md` is a stub pointing at hosted docs; the docs tree adds nothing the source doesn't show. The "sandbox replaces prompt caution" doctrine is source-visible (templates describe, OS enforces; no "please be careful" scaffolding around exec in `default.md` beyond mode-specific test etiquette).

## 9. Strengths

1. **Durable-by-default transcript with typed, versioned line items** and a persist *policy* — resume/fork/compact all read the same artifact; base_instructions frozen per session make replay faithful.
2. **OS-enforced containment with a typed escalation ladder** (execpolicy → sandbox denial evidence → granular approval → request_permissions tool), where prompts only narrate the cage. Network is a first-class sandbox dimension, including MITM-proxy-aware seatbelt profiles.
3. **One metadata table drives all model behavior** (context %, truncation, patch tool type, parallelism, multi-agent version, compaction support), versioned and cache-managed; `comp_hash` makes context-affecting changes explicit and forces clean breaks.
4. **Parallel tool execution with a single RwLock discipline** — cheap, correct-by-construction serialization of mutators, with per-tool opt-in and cancellation semantics.
5. **Compaction as a pluggable multi-engine subsystem** (local/remote/server-reset) with persisted boundary events and post-turn threshold compaction, plus steering-input drain integrated at safe boundaries.
6. **Tool-set size discipline:** tiny core + BM25 `tool_search` deferral beats both "dump 200 MCP tools" and "no discovery".
7. `match`/`not_match` load-time examples in execpolicy rules are a quietly excellent idea — policy as tested code.

## 10. Weaknesses

1. **Massive core.** `session/mod.rs` 5493 lines, `turn.rs` 3279, `mcp_tool_call.rs` 2516; the fork has grown ~90 crates with realtime/voice/guardian/code-mode woven into the same loop. The turn loop's happy path is now littered with feature-gated branches (`Feature::TokenBudget`, `DeferMailboxPreemption`, guardian basic-source checks) — very hard to fork or audit.
2. **Two approval systems at once** (classic AskForApproval flow + Guardian reviewer) with per-mode template text for each — user-facing semantics are hard to predict; budgets/checkpoints for an LLM judge add cost and a new failure domain (the reviewer itself consumes context and can exhaust its budget, `request_budget::ExhaustedReviewBudget`).
3. **OpenAI-shaped coupling:** best compaction (remote V2), experimental context management, model routing/verification, EMA auth all require the ChatGPT backend + plan gating (`session/token_budget.rs:10-18`); local/BYOK gets the plainly-featured path.
4. **No durable execution-status machine:** crash mid-turn recovery is reconstruct-from-rollout + `RecoverTurn` op; there's no per-step durable status like a workflow engine (their own TODO about pre-turn compaction estimating pending input, `turn.rs:189-192`, shows the boundary isn't closed).
5. **Rollout is append-only JSONL with no compaction of storage itself in the hot path** (maintenance/compression are side utilities); long sessions re-scan directory trees for `updated_at` ordering (`list.rs:541-549` concedes this).
6. **Provider replay is not deterministic** — rollout-trace reconstructs semantics after the fact rather than enabling deterministic re-execution; tests lean on huge fixture files.

## 11. Works vs unproven

- **Works (source-visible, production-shaped):** seatbelt/landlock/bwrap execution sandbox incl. escalation-on-denial; unified_exec persistent shells with output budgets; JSONL rollouts + resume/fork + sampling-boundary truncation; local compaction + summary re-injection; parallel/sequential tool gating; apply_patch tolerant matching + streaming diff; execpolicy evaluation; deferred tool search.
- **Real but OpenAI-backend-dependent:** remote compaction V2, model reroute/verification, experimental token-budget context reset, code-mode-only tool exposure (V8 host shipped but `tool_mode` is set only for flagship slugs in `models.json`).
- **Unproven / young:** Guardian automated approvals (checkpoint/budget machinery is new, error paths like `ExhaustedReviewBudget::Compacting` still being patched, `turn.rs:336-355`); realtime voice loop (2770-line `realtime_conversation.rs` alongside a "basic session source" special-casing spilling into `run_turn`); multi-agent v2 message board vs legacy collab tools coexist (two event families persisted); Windows MXC availability heuristics (`record_availability_once`).

## 12. What Zero Code should learn

1. **Adopt the sandbox-vs-permission-prompt trade explicitly.** Codex proves the prompt can shrink to "here is what your cage is" (`prompts/templates/permissions/sandbox_mode/*.md`) because enforcement is OS-level with typed escalation (`SandboxErr::Denied` → approval widens only what was approved, `tools/sandboxing.rs:255-258`). Zero's bash-permission prompts + shadow-git checkpoint model is the *inverse* (prompt-first, undo-as-backstop): keep it for the default agent, but add (a) a durable deny-evidence classification so "retry with escalation" is a typed state, not a stderr guess, and (b) protected-path semantics (`.git`, config dirs) *inside* writable roots — the `WritableRoot.read_only_subpaths` + metadata-name regex pattern is directly liftable.
2. **Rollout durability bar.** Zero's V2 durable `session_input` is the right start; Codex's deltas: a typed persist *policy* module (what event kinds hit durable history, `rollout/src/policy.rs`), flush-ack semantics with writer-recovery (`recorder.rs:1065-1192`), a `SessionMeta` line that freezes base_instructions/cwd/model for faithful resume, and fork-truncation at the last *sampling boundary* (never mid-turn). Zero's V2 "admit then promote at safe boundary" already matches the boundary idea; the meta-line and persist-policy are cheap adds.
3. **Model-metadata discipline.** Zero scatters model behavior (context limits, cache behavior, tool support) across config + code. `ModelInfo`/`models.json` shows the converged shape: one versioned table with `effective_context_window_percent`, truncation policy per model, behavior switches (parallel tools, patch tool type), plus a `comp_hash`-style fingerprint whose change *forces compaction* on model switch. Zero's gpt-5 path already inherits Codex-style behavior; make the table the single source instead of per-id `if`s.
4. **apply_patch:** Zero's Codex-style patch tool should copy `seek_sequence`'s monotone relaxation ladder (exact → trailing-ws → both-ws, EOF-anchored first) and the in-memory derive-then-write flow with unified-diff generated for display only (`file_update.rs:25-204`) — it pairs perfectly with Zero's 9-stage edit matcher; the *streaming parser* (live diff while tokens arrive) is a visible UX win Zero's edit tools can adopt via existing streaming.
5. **Compaction as engines behind one trigger.** Zero's cache-continuation summaries are aligned with Codex's local engine; the transferable ideas are: compaction boundaries as persisted events (`ContextCompacted`) so replay matches, a post-turn percent threshold (compact *after* a turn, before the next prompt), and stripping context-affecting drift (model/prefix changes) into the trigger via a comp hash.
6. **Tool-set size philosophy validates Zero's tool_search/code-mode direction** — Codex landed on "tiny always-on core + BM25 deferred discovery + model-gated code-mode". Zero's four overlapping discovery layers (baseline #6) should converge on this one vocabulary: exposure levels + one search tool, not registry × repair × search × code-mode.
7. **Parallel-tool RwLock pattern** is a one-file adoption for Zero's tool loop: mutators take the write lock, readers fan out — cheaper than Zero's current sequencing and it composes with background shells.
8. **Guardian is worth watching, not copying:** LLM-triaged approvals with durable budget/decision accounting is plausibly the end-state for approval fatigue, but its double-system user-visible semantics and new failure modes show the cost of doing it before the deterministic policy layer (execpolicy-style, with load-time `match`/`not_match` tests — steal that regardless) is trusted. One design detail worth stealing cheaply: reviewer/triage sessions run as a *degraded session class* (`is_basic_session_source` gates skill catalogs, plugin mentions, remote git discovery, and evidence budgets inside `run_turn`, `turn.rs:181,207,315,514-518`) — the judge is deliberately fed less than the worker.
